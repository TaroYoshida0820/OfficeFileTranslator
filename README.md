構造保持型 多言語翻訳パイプライン

Word文書(.docx/.docm)を、レイアウト・書式・表構造を一切崩さずに多言語翻訳するツールです。

Copilotに.docmファイルの翻訳を頼んだところ表がズレる・書式が飛ぶ、という経験がきっかけで自作しました。

⚠️ 本リポジトリは架空のポートフォリオ企画「AEC PoC評価ボードプロジェクト」のサンプルデータのみを含みます。

特徴
書式を保ったまま翻訳: docxの実体であるXML(OOXML)を直接解析し、書式境界(ラン)を保ったままテキストを抽出・再挿入します。
表・改ページ・太字・ハイパーリンク等は無傷のまま保持されます。
識別子の自動保護: 信号名・要求ID・仕様書IDのような、翻訳してはいけない文字列を正規表現で検出し、翻訳エンジンに一切触れさせずに保護します。
言語非依存の設計: 抽出・再構築のロジックは言語に依存しません。用語集(Excel)を差し替えるだけで、対応言語を追加できます。
実行前の無料見積もり: 実際にAPIを呼ぶ前に、翻訳対象のボリューム・概算コストを確認できます。

アーキテクチャ
┌─────────────────────────────────────┐
│ 運搬層(言語非依存)                    │
│   docx → Zip展開 → XML解析            │
│   → ラン結合(書式境界を保持)          │
│   → [翻訳] → 同一ノードへ再挿入        │
│   → Zip再構築 → docx                  │
├─────────────────────────────────────┤
│ 頭脳層(言語ペアごとに差し替え)         │
│   翻訳API呼び出し + 用語集(RAG)       │
├─────────────────────────────────────┤
│ 保護層(全言語共通)                    │
│   信号名・REQ-ID・SPEC-ID等を          │
│   翻訳対象から自動的に除外             │
└─────────────────────────────────────┘

使い方
1. 事前見積もり(推奨・無料)

本番実行前に、翻訳対象のボリュームと概算コストを確認できます。ネットワーク通信は行いません。

bash
python estimate.py "input.docx"
2. 翻訳の実行
bash
python run_translation.py "input.docx" "output.docx" --lang en --glossary "AEC_翻訳用語集.xlsx"

--langは en(英語) / zh(簡体中文) / vi(ベトナム語)に対応しています。

用語集について

AEC_翻訳用語集.xlsxは以下の3シートで構成されています。

シート	内容
00_README	対応言語・運用ルールのメモ
01_翻訳用語集	一般用語の対訳リスト(翻訳APIへのヒントとして使用)
02_識別子_翻訳禁止	翻訳してはいけない識別子のパターン一覧

新しい言語や用語を追加したい場合は、このExcelファイルを編集するだけで反映されます。

対応言語の状況
言語ペア	状態
日 ⇔ 英	実装・動作検証済み
日 ⇔ 中(簡体字)	パイプラインは対応済み。用語集エントリは今後拡充予定
日 ⇔ 越	パイプラインは対応済み。用語集エントリは今後拡充予定

パイプライン(抽出・ラン結合・再挿入)は言語非依存のため、上記以外の言語ペアも用語集を追加するだけで理論上は対応できます。

既知の制約
画像内テキストは翻訳対象外: フローチャート等、ラスター画像(PNG等)に焼き込まれたテキストは処理できません。
SVGで図を作成する運用に変更すれば対応可能ですが、別途プレビュー画像の再レンダリング工程が必要になります。
人間が編集したWordファイルでの再検証が未実施: 現在の検証はプログラム生成されたdocxで行っており、
Word上で長期間手編集されたファイル特有のラン分断パターンでの動作確認は今後の課題です。
API呼び出しコストの最適化余地: 現行は段落単位でAPIを呼び出すため、大規模文書では呼び出し回数(固定オーバーヘッド)がコストに影響します。
複数段落をまとめてバッチ化する改善を検討中です。
